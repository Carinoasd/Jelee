# 持久批次匯入任務

下一段在既有 jobs 佇列加入 `catalog_import`，每批明確選定1至100個同次掃描的影片候選。沿用每庫一個活動任務、容量限制、手動／背景公平、租約、取消與重啟恢復。來源檔案核對在交易外，單筆建立條目與保存進度必須同一短交易，失去租約的 worker 不得提交。

## 保存與處理

- 新 migration 保存來源掃描、不可變輸入與逐筆進度；不改001–039。只有具有匯入能力的 worker 能領取新種類。
- 來源必須是最新已接受掃描；解析來源的「較新掃描」判斷只比較 inventory_scan，避免新建的匯入任務使自己的來源失效。
- 活動批次保留其來源掃描，完成後才允許既有歷史保留策略回收。歷史回收後不承諾重播仍能重新讀取原盤點。
- 每筆成功後保存item／source ID，恢復跳過已完成項目。相同位置且相同輸入回傳既有ID；不同資料衝突，不覆蓋人工修改。
- 取消或失敗保留已提交前綴，未完成部分保持未匯入；報告清楚呈現這種部分完成，不宣稱整批交易回滾。原媒體不變。
- 新請求以Idempotency-Key保留意圖；同key異意圖衝突。啟動時重新查管理員授權，執行採已提交持久意圖與worker租約。

## 驗收

正式API／worker／檔案／PG流程，多筆成功與相同請求重試；來源失效、候選變更、容量與權限拒絕；取消、owner失效、恢復不重複寫入；交易故障不留下item而漏存進度；活動來源不被歷史清理；遷移up/down/up及有保留資料的降版拒絕。規模與全庫自動辨識另驗收，100筆有界任務不冒充全庫自動匯入。

schema40與正式API／worker已實作並完成本地驗收，見[操作契約](catalog-import-jobs.md)。
