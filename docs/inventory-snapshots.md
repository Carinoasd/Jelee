# 分批準備與發布清單基準

## 問題與行為

十萬檔案的實測發現，掃描後把整份清單複製到接受基準，會超過 worker 的兩秒資料庫期限，並讓狀態查詢等待工作鎖逾時。schema43 新增基準快照：先分批準備不可見資料，完成後才在短交易中切換目前基準與任務終態。

正式 worker 在掃描／probe／NFO 執行完成後，保持原有 heartbeat 與取消監視，每次準備最多 128 筆。游標、已複製數量與資料同交易提交；中斷後新租約持有者接續同一游標。準備期間，現有查詢仍看到完整舊基準。

每批核對工作租約、取消旗標、媒體庫根世代、前一快照與基準版號。資料庫時鐘決定租約效期，批次最後再次檢查。根目錄或基準改變時拒絕準備；未完成或筆數不符時不能發布。FinishJob 仍檢查完整範圍、缺失保護與媒體前置階段，切換後再做租約末端檢查；交易中到期會連同指標及終態一起回滾。

## 進度查詢

單筆工作狀態查詢改讀已提交的 MVCC 狀態，不再取得 worker 的全域寫入鎖。查詢仍使用帳號交易，並在讀取前後驗證管理員與會話；取消、重試及其他變更仍保留原有寫入鎖順序。持鎖期間的狀態讀取與心跳／取消競爭各有真實 PostgreSQL 回歸測試。

## 儲存與相容

`library_inventory_baseline_data` 保存快照列；`libraries.active_inventory_snapshot` 指向目前快照。原 `library_inventory_baseline` 名稱保留為可更新 view，只顯示目前快照；舊資料使用快照零。快照專用鍵、快照游標索引與既有排序索引並存。比對及忽略分頁先讀取目前快照鍵，再以實體表索引定位；不讓 view 的基數估算造成重複全表掃描。

新一輪準備先分批清理不可見舊快照，每次最多 512 筆，不刪目前基準或本次待發布資料。清理完成才開始複製新快照，因此中斷重試不會持續累積完整副本。接受基準獨立於工作歷史，裁剪歷史不會刪掉目前資料。

本機原型已驗證 view 的新增、更新及刪除只影響可見快照。正式回歸另檢查有、無 ANALYZE 統計時的比對列數與分頁上限；實測曾揭露原型未涵蓋的計畫退化，因此正式讀取改用明確快照鍵。可更新 view 與 CHECK OPTION 的規則參照 [PostgreSQL 16 CREATE VIEW](https://www.postgresql.org/docs/16/sql-createview.html)；仍以正式查詢的回歸及 EXPLAIN 為準。

001–042 的八十四份已發布 SQL 保持不變。schema43 降版只接受尚未保留快照及準備狀態的資料庫，否則拒絕，避免靜默丟失基準。

## 新鮮資料的查詢計畫

一萬檔案重掃曾因統計尚未更新，讓索引逐列掃描大量候選；工作等租約重試後才成功，耗時約 61 秒。診斷保存了逾時 SQL 與 EXPLAIN。缺失比對改用集合差，圖片目前狀態改用一次分組，避免依賴逐筆查詢的低估成本。測試同時涵蓋未 ANALYZE 與已 ANALYZE 的計數和實際讀取列數。規模測試現在要求 attempts=1，重試後成功也不算效能驗收通過。

## 本段邊界

忽略規則的發布還需要合併 excluded 歷史列與驗證封印，本段保持其原有發布流程，尚未把大規模忽略合併算成通過。內部直接呼叫 FinishJob、未走正式 worker 準備介面的既有小型契約，也保留原同步發布路徑。

快照只處理衍生清單資料，不修改原始媒體、NFO 或圖片。這不構成整個檔案系統的原子快照；檔案可在掃描後變動，後續事件或定時掃描仍需重新核對。

本段完成以下純清單量測與回歸。四核心、圖片負載、容器 OOM、混合任務及二十四小時穩態仍另行驗收。
