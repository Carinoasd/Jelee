# 掃描規模與穩定性驗收計畫

對應第三階段 3D、G42.3／G42.8–10 與 G41.8–10；不把純清單掃描當成圖片處理或混合媒體探測的完整驗收。

1. 使用專用 jelee_test 資料庫中的隨機自有 schema 與 Linux 原生 ext4 專用臨時目錄（不用記憶體 tmpfs）。實際建立一萬、十萬、五十萬個小檔；資料生成不算掃描耗時。檔案命名確定、內容自製，執行後清理自己的資料。
2. 執行正式 Scanner → worker → PostgreSQL 入庫及完成流程；核對終態、數量、批次上限與原檔抽樣雜湊。每檔大小不能被當成真實影片探測的負載。
3. 在 GOMAXPROCS=2／4 下（不是硬體 CPU 配額）記錄吞吐、heap、RSS、GC 暫停、goroutine、FD 與 DB 池。Go 記憶體限制明列，不把 WSL 主機環境稱為容器 OOM 驗收。
4. 每檔位跑首次與不變重掃，保存分時樣本及強制 GC 前後的 heap profile。取樣與輸出有界；結果不保存路徑、密碼或 DSN。
5. 長測獨立 schema 與程序，在實際時間下反覆掃描、事件變更及取消／恢復；保留樣本與起迄時間。未達二十四小時只能報當前實際時長，不能加速時鐘冒充資源穩態。
6. 真正觀察到的峰值建立有餘裕的預算；先保存基線，若需要優化，再用同條件重跑相關檔位。驗收失敗保留結果，不修改門檻使其假通過。

監看階段已以 `6ddacf1f2c` 發布。本段新增 Linux opt-in 真實清單測試，每次使用一個正式 worker、預設租約與資料庫期限、128 項批次、GOMEMLIMIT=512MiB；測試起迄包含工作輪詢，素材建立及 heap profile 不計入掃描耗時。每秒取樣，因此峰值是取樣觀測值。

先量測一萬檔案原實作，再以真實 pgx query tracer 重現每批 SQL 往返：128 檔案 395 次、128 目錄 267 次。優化只合併批次讀取／寫入，保持逐項容量及溢位判斷、檔案與目錄衝突、重播 ID、同交易資料與計數、租約到期守衛；不修改已發佈的遷移。回歸包含故意衝突的整批回滾及原有晚到租約測試。

環境初查：WSL2 Linux 6.18.33.2、16 邏輯 CPU、約 14.9 GiB RAM；/tmp 為 tmpfs 且只剩約 2.1 GiB。使用者家目錄所在 ext4 約有 833 GiB 可用，後續測試以專用 mkdtemp 目錄及可用空間／inode 前檢執行。執行時須重新記錄實際負載與空間；這些數字只是初查。
