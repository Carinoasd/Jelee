# 十萬本地圖片記憶體驗收

狀態：修正輸出緩衝配置後，千張短測試與正式十萬張驗收通過。首輪 GC 比例超標的失敗結果完整保留，門檻未放寬。[來源與實測證據](evidence/image-memory.json)記錄前後結果；圖片功能見[本地海報](local-images.md)。

## 範圍與固定目標

這一輪使用正式 Fx、HTTP、PostgreSQL、預設密碼雜湊與圖片處理器，處理十萬個不同項目、來源及原圖檔。每張都經權限查詢、串流暫存、完整解碼、縮小及 JPEG 編碼，再透過 HTTP 傳完。產生的圖片共用三種固定畫面；不同來源不代表十萬種不同畫面。

[預算](../tools/image-memory-budget.json)在正式執行前固定：2 CPUs、GOMAXPROCS=2、GOGC=100、Go soft limit 512 MiB、容器 768 MiB、禁用 swap。程序 RSS 上限 464 MiB 是沿用現有容量目標的工程門檻，尚不是圖片負載實測基線。GC 暫停桶的保守上界須不超過 50 ms；counter 累計及 histogram 上界總和，各自不得超過其觀測間隔的 1%。

沿用正式圖片預設：兩個准入槽、每張 96 MiB 配置預算、16 MiB 原圖上限、2 MiB 編碼輸出上限、32 MiB／128 筆快取及 300 秒 TTL。原圖維持唯讀，暫存放在獨立 64 MiB、UID/GID 65532、0700 的 tmpfs；它的記憶體仍計入容器使用量。

## 素材與成功判定

| 集合 | 正式數量 | 千張短測試 | 尺寸 | 縮圖請求 |
| --- | ---: | ---: | --- | --- |
| JPEG | 95000 | 900 | 640 × 960 | 160 × 240 |
| 透明 PNG | 4936 | 36 | 256 × 384 | 160 × 240 |
| 16-bit PNG | 64 | 64 | 4096 × 2560 | 1024 × 1024，等比例得到 1024 × 640 |

每十個項目共用一個小目錄，原圖及合成影片定位檔各自是獨立一般檔案。測試用影片定位檔不含真實影片資料。產生器只寫入本次新建、空白且私有的原生 Linux 目錄；不讀使用者媒體，也不下載圖片。

兩個 HTTP 客戶端處理整個冷集合，不能用沒有記錄的重試掩蓋失敗。冷集合指圖片處理器的快取沒有命中；本輪沒有清除作業系統的檔案快取。每筆必須回 200、符合輸出尺寸與格式，完整傳輸的 SHA256 必須符合強 ETag。冷輪前後的 admitted、completed、misses、decodes 均應增加十萬，hits 不增加；解碼計數在呼叫前遞增，因此必須同時核對所有成功回應。只保留固定大小的結果與抽樣，不累存十萬張輸出。

最後 64 張 JPEG 另做 GET、HEAD、304，共 192 次暖請求，要求快取命中且沒有新解碼。兩輪分開記錄命中率。每秒及階段邊界採樣 RSS、heap、GC 與處理器聚合上限；最多 3664 筆，採樣間隔不得超過 5 秒，總時間上限一小時。這是測試資源界線，並非產品速度承諾。

## 負例、停止與清理

主成功集合之外另放不支援格式、截斷 JPEG、16 MiB 加 1 byte 原圖、巨大尺寸 PNG 標頭。巨大標頭的目的是驗證解碼前拒絕，不能算成真正大圖解碼成功。

小組驗證另涵蓋未登入、無權限、暖圖片撤權、滿載 503、取消與恢復。透過測試資料庫的短暫鎖定確認 HTTP 請求正在等待，再測取消及 SIGTERM 停止；這不代表 CPU 解碼可在任意指令瞬間中斷。既有處理器單元測試負責確認取消後仍持有解碼槽。

容器以非 root、唯讀根與媒體、移除 capabilities 及 no-new-privileges 執行。外層核對退出狀態與 OOM，保留失敗證據並清理本次自建容器、映像、schema、憑證及素材。既有專用 PostgreSQL 容器保留。原圖完整性證據是唯讀掛載與固定抽樣前後比對，不能宣稱全部十萬張都前後重算雜湊。

## 執行

需要原生 Linux Docker、已固定工具鏈、專用 `jelee_test` PostgreSQL、至少 20 GiB 可用空間及足夠 inode。資料庫 URL 以私有環境變數提供，勿寫入命令列或提交：

```sh
JELEE_IMAGE_MEMORY_PG_CONTAINER=<專用測試容器名稱> make image-memory-smoke-test
JELEE_IMAGE_MEMORY_PG_CONTAINER=<專用測試容器名稱> make image-memory-test
```

控制器亦讀取私有 `JELEE_TEST_DATABASE_URL`。短測試一律標為 `finalAcceptance=false`。一般 CI 的記憶體契約步驟會執行圖片驗證器、控制器及 sampler 的小型測試，不把它們算成十萬張驗收。

## 正式結果

| 指標 | 修後千張短測試 | 修後十萬張正式驗收 |
| --- | ---: | ---: |
| 冷輪成功 GET／實際解碼 | 1,000／1,000 | 100,000／100,000 |
| 冷輪時間 | 8.16 秒 | 787.89 秒 |
| 全段觀測 | 12.55 秒 | 807.56 秒 |
| 程序 RSS 峰值 | 433.26 MiB | 355.55 MiB |
| 暖 GET／HEAD／304 命中 | 192／192 | 192／192 |

正式驗收取得 816 筆 RSS 樣本，heap 峰值 248.26 MiB。GC 49,088 cycles、98,176 個暫停事件，最高暫停桶上界 0.524288 ms；counter 暫停比例 0.39286%、histogram 保守上界比例 0.42921%，均通過原 50 ms／1% 門檻。冷輪沒有命中或失敗，暖輪沒有新增解碼。兩槽准入、超大圖拒絕、權限、取消復原、SIGTERM、原檔抽樣與自建資源清理通過；退出 0，沒有 OOM。

本輪冷處理時間比首輪 380.85 秒長，未隔離環境或分析原因，因此不宣稱吞吐提升。配置量下降、RSS／GC 門檻通過與實測時間分開呈現。短測試包含相同 64 張大 PNG，峰值也不應按項目數線性外推。

最終 920 份來源在量測期間保持。新增驗收工具的 Windows Go 84 通過／2 略過、Linux race 85／2；兩個略過項需要明確選用原生規模驗收。Python 圖片驗證器／控制器及既有掃描回歸共 33 項通過，完整 CI 契約 12 步通過。Linux 控制器測試初輪因 Windows 掛載不保留唯讀 mode 而失敗，僅將其測試目錄改為原生暫存後重驗；沒有削弱控制器檢查。配置修正後的產品回歸另列下節。

## 仍未完成

G40.13 的其他圖片角色、格式、命名及來源與 G42.10 的至少 24 小時穩態仍須另外完成。本輪量測版本的同尺寸副本缺口，已由後續[同尺寸修正](image-same-size.md)處理；這裡保留原量測版本的證據。這一輪不取代既有[五十萬掃描](scan-memory.md)及[heap 前後比較](heap-profile.md)的各自證據，也不代表整機或所有混合負載已達標。

## 首輪失敗與修正

首輪十萬張均成功，冷處理 380.85 秒、全段觀測 399.45 秒，採樣 RSS 峰值 412.65 MiB；停止與清理通過。但 GC counter 暫停比例 1.30739%、histogram 保守上界比例 1.44244%，均超過事前 1% 門檻，因此整體記為失敗。最高暫停桶上界 6.291456 ms 通過 50 ms 門檻，不能用它抵銷累計比例失敗。

圖片編碼原本每次預先配置完整 2 MiB 輸出緩衝，即使最後 JPEG 只有數 KiB。修正為按需從最多 4 KiB 起始、倍增並限制容量，超限時不修改既有輸出；最後仍複製到恰好大小的獨立快取資料。成長時的新舊緩衝及最後複製皆保持原來的兩份輸出預算，沒有新增常駐 pool 或更改准入與停止流程。

實際 16×8 冷縮圖回歸先測得每筆 2,438,565 bytes，超過 1 MiB 測試門檻；修後為 309,049 bytes。完整 Windows 圖片套件 56 個通過事件、1 個平台略過，HTTP 圖片 44／0；Linux race 圖片 42／0、HTTP 44／0，tagged vet 與三個正式命令建置通過。事件包含父與子測試。固定 RSS／GC 門檻、圖片來源、正式 KDF 與負載數量保持，修後已重新執行並通過短測試與十萬張驗收。
