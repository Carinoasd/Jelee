# NFO 項目跨讀取的實體身分重核

當前binary要求schema26；本頁保留先前階段的契約與證據。缺少文字值時的獨立NFO鎖及升降版限制，見[第25版契約](nfo-field-lock-intent.md)；有效lock-only投影見[第26版契約](nfo-lock-only.md)。

本頁保留該階段的實作與驗證；後續第24版的三態保存及可信缺失／損壞回退，見[最新回退契約](nfo-tmdb-fallback.md)。

正式讀者現在提供自身持有的觀察物件。它保存根目錄、父目錄、媒體檔與選中 NFO 的檔案系統身分，以及欄位與候選名稱觀察；檔案 handle 全部在讀取結束時關閉，不在供應商等待期間保留。

## 最終套用前重核

NFO-only 套用前，及 TMDB 詳情取得後，應用呼叫觀察物件的 `Recheck`。讀者重新安全選擇與完整讀取，再以 `os.SameFile`／檔案資訊比對根目錄、父目錄、媒體檔及 NFO 實體。選中 NFO 的大小與時間戳也必須和完整讀取的檔案戳一致。

即使 NFO 名稱、內容、SHA256、大小與時間戳完全一致，根目錄、父目錄、媒體檔或 NFO 實體替換仍回傳 409。先前有效的 NFO 在查詢期间消失，也回傳 409；首次即缺失仍是 503。應用另保持原本的候選集合、選名、完整雜湊、解析身分、欄位及鎖意圖比較；最後資料庫交易仍重驗 session、版本、種類、來源與 NFO 世代。

呼叫者取得的是複製的欄位與鎖清單，修改不影響觀察物件。檔案系統資訊、根路徑、私有 scope 與重核物件不進 HTTP 或稽核。正式 runtime 與 NFO-only 整合讀者均走此觀察介面；舊內部測試讀者保留其原選擇／單檔契約。

## 驗證

Windows 與 Linux 真檔案驗根目錄、父目錄、媒體與 NFO 的實體替換，保留相同 NFO 內容／檔案戳與候選名稱，確認舊文字比較仍相同而新實體重核拒絕；另驗欄位與鎖的呼叫者隔離。

正式 TCP HTTP／受控 TLS 供應商／安全 NFO／PostgreSQL 在供應商請求中執行四種替換，資料庫根路徑與來源 ID 保持，確認 409、版本／分類／欄位不變、零套用稽核。原檔由測試備份保持並復原；這些替換只發生在測試持有的暫存目錄。刻意停用正式讀者的跨讀取實體比較，完整路徑必須因接受替換後寫入而失敗；隨後逐位元復原並重跑。詳見[執行證據](evidence/nfo-item-observation.json)。

## 範圍

目前觀察仍只接受有效、可套用的四欄 NFO。缺失／損壞的供應商回退與狀態持久化尚未啟用；其他 NFO 欄位、季／集、多項目、實際匯入／worker／階層、無損回寫、清除外部資料及前端仍未完成。沿用 schema23，原 001–023 保持。

這是重核檢查點，不是檔案系統原子快照；最後觀察後仍可能改變，阻塞檔案系統操作無硬性取消保證。原媒體、NFO、圖片及授權文件保持；G14／G39、第三階段與全案仍未完成。
