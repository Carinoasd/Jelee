# ADR 0002：不引入 Redis；快取留在行程內記憶體，跨實例協調用 PostgreSQL

- 狀態：已採納
- 日期：2026-10-04
- 相關需求：G04.7（另涉及 G04.5 事務與並發、G37 部署、G45 開發者模式、G47 客戶端管控）
- 相關程式：`internal/platform/cache/`、`internal/adapter/images/`（`cache.go`、`store.go`）、`internal/adapter/http/`（`client_control.go`、`site_settings.go`、`setup.go`、`login_limiter.go`）、`internal/platform/devmode/controller.go`、`internal/adapter/metadata/movie_cache.go`、`internal/adapter/postgres/`（`probe_cache.go`、`nfo_cache.go`、`jobs*.go`、各處 `pg_advisory_*`）
- 盤點與各項保證：[快取邊界](../cache-boundaries.md)

## 需求原文

> G04.7 缓存边界：Redis（可选）只做缓存/锁；失效以版本号或事件驱动；不可用时降级而非错误。

原文有三條約束：(1) Redis 是**可選**的，若使用也只能做快取或鎖，不能成為資料來源；(2) 快取失效要靠版本號或事件，不能只靠時間；(3) 快取或鎖的後端不可用時要降級，不能讓請求直接失敗。

## 決定

Jelee 不引入 Redis，`go.mod` 也沒有任何 Redis 客戶端。

1. **快取一律放在行程內記憶體**，而且都有上限（筆數、位元組，或兩者都有）。能用內容定址的（圖片輸出、圖片變體、忽略規則程式、字幕 UTF-8 複本、探測／NFO 快取的檔案戳記），鍵本身就是版本，內容一變鍵就跟著變，不需要另外失效。其餘的以資料庫的版本欄位，或本實例的寫入事件來失效。
2. **跨實例協調只用 PostgreSQL**：交易級 advisory lock（`pg_advisory_xact_lock`／`pg_try_advisory_xact_lock`）、工作階段級 advisory lock（只有舊庫匯入使用）、帶 generation 防護的任務租約（`jobs.lease_until`／`generation`）、探測租約、監看租約，以及在同一交易內遞增的版本欄位（例如 `client_control_policy.version`、`dev_mode_state.version`、`site_appearance.revision`）。目前沒有使用 `LISTEN`／`NOTIFY`。
3. **快取來源不可用時一律沿用上次的值**，或退回安全的預設值，並寫入記錄。只有兩類例外會直接回錯誤：一是安全閘門（初始設定閘門、分享訪客稽核），二是本來就必須查資料庫的請求（驗證工作階段、讀取媒體庫）。對它們來說，「降級」等於放行，所以這裡刻意「失敗即關閉」（fail closed）。

## 為什麼不用 Redis

- **資料來源只有一個。** 所有權威狀態都在 PostgreSQL。Redis 若只當快取，等於在資料庫前面再加一層要失效的副本，而版本號本來就存在資料庫裡，每個請求已經會順便讀到（客戶端管控的版本跟著工作階段查詢一起取回），不需要第二個系統來廣播。
- **鎖已經有了，而且跟資料同交易。** advisory lock 在交易結束時自動釋放，和被保護的寫入一起提交或回滾，不會出現「鎖還在、資料已回滾」或「鎖過期、交易還在跑」。Redis 鎖（含 Redlock）做不到這種原子性，還得另外處理 fencing token；Jelee 的任務租約已經用 `generation` 做 fencing。
- **部署目標是單機或少數實例。** 媒體伺服器的熱路徑是串流與圖片，不是共享快取的命中率。多加一個必要的服務，就多一個要監控、備份、升級的元件，也多一個故障點。需求寫明 Redis 是「可選」，不引入它仍然符合原文。
- **降級更簡單。** 沒有外部快取，就沒有「快取後端不可用」這種狀態。剩下的降級情境只有「資料庫暫時讀不到」，各快取都已定義為沿用上次的值（見盤點表的「來源不可用」欄）。

## 代價與限制

- **各實例的計數器互不相通。** 登入限速（IP 與帳號桶）、客戶端管控的 `rate_limit` 動作、直接串流的並發與頻寬上限、TMDB 請求節流，都是各實例自己算。部署 N 個實例時，最寬鬆的情況下實際上限是設定值的 N 倍。帳號鎖定（密碼錯誤次數）寫在資料庫裡，全域一致，不受影響。
- **少數快取跨實例是「有上限的延遲」，不是即時。** 前端 CSP 的外部字型白名單：本實例寫入後立即失效，其他實例最多延遲 30 秒。開發者模式：其他實例在輪詢間隔內（可啟用開發者模式的實例 2 秒，其他 10 秒）跟上，到期則依本機時鐘立即生效。初始設定完成：其他實例最多延遲 1 秒放行。這些延遲只會讓變更晚一點生效，不會讓實例讀到錯誤的資料。
- **TMDB 候選快取只靠 TTL（24 小時）。** 外部來源沒有版本號可用。候選資料都附有 `fetchedAt`，錯誤結果從不快取；供應商不可用時回錯誤，不改用過期資料，因為候選資料會被套用成媒體庫的中繼資料，套用過期內容比讓管理員稍後重試更糟。

## 何時值得重新考慮 Redis

出現以下任一情況時，應重新評估。屆時 Redis 仍只能做快取或鎖，失效仍以資料庫版本號為準，Redis 不可用時要退回本 ADR 的行程內行為：

1. **需要跨實例的精確限流**：例如要求 N 個實例合計的登入嘗試、客戶端 `rate_limit` 或每位使用者的串流數有全域上限，而且無法用「每實例上限 = 全域上限 / N」近似。也可以先評估用 PostgreSQL 的計數表或 advisory lock 實作，只有在寫入量超過資料庫負荷時才改用 Redis。
2. **多實例規模變大**：實例數多到各自重複載入與編譯（客戶端規則、CSP）造成可量測的資料庫負擔，或 30 秒、10 秒等跨實例延遲已經不能接受，需要即時廣播。此時應先考慮 PostgreSQL `LISTEN`／`NOTIFY`，它不需要新元件。
3. **需要跨實例共用、計算昂貴的快取**：例如轉碼片段、大量圖片變體要在多台機器間共用，而本機磁碟快取的重複計算成本已經可以量測。
4. **工作階段查詢成為瓶頸**：每個請求都要查一次資料庫來驗證工作階段，若在壓測中確認這是瓶頸，可以考慮快取工作階段。前提是撤銷仍要即時生效，也就是撤銷時遞增版本並廣播。

## 後果與守門

- 新增快取時，必須在 [快取邊界](../cache-boundaries.md) 盤點表登記：存放位置、鍵、上限、失效方式、多實例行為、來源不可用時的行為，並附上降級測試。共用快取只能放對所有呼叫者都相同的資料（見 `internal/platform/cache` 套件說明）。
- 新增跨實例協調時，優先使用交易級 advisory lock 或帶 generation 的租約；lock key 比照既有寫法，用 `hashtext(current_schema())` 加上固定常數（或固定的 `hashtext('jelee.<用途>')`），並在 [快取邊界](../cache-boundaries.md#跨實例協調) 登記。
- 引入任何 Redis 依賴都必須先修訂本 ADR。
