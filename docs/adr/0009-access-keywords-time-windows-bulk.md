# ADR 0009：關鍵字封鎖、限制時段、分級代碼表與批量授權

- 狀態：已採納
- 日期：2026-10-06
- 相關需求：G48.4、G48.7（並推進 G48.8、G48.10）
- 相關程式：`internal/adapter/postgres/visibility.go`（`keywordsClearSQL`、`activeWindowsSQL`、`grantVisibleSQL`）、`content_access.go`、`access_bulk.go`、`internal/domain/access_admin.go`、遷移 `000084_access_controls`
- 詳細規則：[存取控制](../access-control.md)

## 需求原文

> G48.4 分级与内容控制：按分级、标签、关键字屏蔽；支持时间窗（如限制时段）；不同用户可不同分级上限；分级缺失时的默认策略可配。
>
> G48.7 管理体验：库授权矩阵页面（用户 × 库批量勾选）、批量应用、模板（如“成人库”“儿童库”）、变更预览（影响多少条目/用户）、变更写审计。

## 決定

1. **關鍵字比對標題，不比對簡介。** 比對條目與其祖先（季、劇集）的掃描標題（`items.title`）、中繼資料標題（`title`）與原名（`originalTitle`）；兩邊都做 NFKC 正規化（全形／半形英數與片假名視為相同）、去頭尾空白、轉小寫，子字串命中即隱藏。
2. **「限制時段」是「時段內套用限制」，不是「時段外禁止」。** 每位使用者最多 20 個時段，每個時段有星期幾、開始、結束（可跨午夜，屬於開始的那天）、IANA 時區與可選的分級上限：
   - 沒有分級上限：時段內**隱藏全部內容**（整個帳號看不到任何條目，也不能直投）；
   - 有分級上限：時段內的有效上限＝`min(使用者上限, 時段上限)`，未分級條目照使用者／全域的未分級策略。
   - 條目 `allow` 規則**不能**越過時段；時段只作用於受限使用者，管理員照 `restrict_admins` 決定。
3. **時區逐時段指定，沒有「伺服器時區」預設。** 時段一律帶 IANA 名稱（不接受 `Local`），寫入時同時以 Go 與 PostgreSQL（`pg_timezone_names`）驗證；管理介面預填瀏覽器時區。
4. **時間用請求時刻並下推到同一條 SQL。** HTTP 層在驗證後把請求時刻放進 `access.RequestScope.At`，隨既有的單一 jsonb 請求參數（`requestScopeArg` 的 `at`）進入統一述詞；述詞以 `AT TIME ZONE` 換成各時段的當地時間判斷。沒有請求的語句（背景工作）用 `statement_timestamp()`。時鐘可由 `httpapi.WithAccessClock` 注入；儲存層測試直接在 principal 放時刻。
5. **分級代碼表可由管理員整表替換**（`PUT /api/v1/access/parental-ratings`），預設內容就是遷移 069 內建的表，所以不設定就是原行為。代碼以篩選器相同的正規化儲存；帶 `Rated `、兩字母國碼前綴（篩選器比對前會去掉，永遠比不到）或正規化後重複的代碼一律拒絕。
6. **批量授權與模板都先預覽、後套用，兩者走同一段程式。** 預覽與套用在同一個交易裡做完全相同的變更：變更前把受影響使用者「看得到的使用者 × 條目」存進交易暫存表，變更後以同一個統一述詞（`grantVisibleSQL`＝`itemVisibleSQL` 去掉每請求的網路限制）再算一次並比較；預覽回滾，套用提交並把同一組數字寫進稽核。
7. **模板是「複製」不是「連結」。** 套用模板＝把使用者的媒體庫授權設成模板的庫集合、把分級上限／未分級策略／封鎖標籤／關鍵字整組換成模板的；之後修改或刪除模板不影響已套用的使用者。條目規則與限制時段不在模板裡，套用時保留。

## 理由

- **簡介產生大量誤判**：家長控制的關鍵字通常是片名用語；簡介裡「殺人鯨」「戰爭」之類的字會把大量無關內容藏掉，而且簡介可達 16 KiB，每列正規化的成本遠高於標題。主題性的封鎖已有標籤／類型（G48.4 的「標籤」），關鍵字補的是沒有標籤的條目。
- **「限制時段」的字面是「時段內限制」**：需求舉例「如限制時段」。上游 Jellyfin 的 AccessSchedule 是「允許時段」，兩者可互相表達（允許 08:00–21:00 等於限制 21:00–08:00），但限制時段可以同時表達「晚上只看普遍級」這種分級收緊，允許時段不能。時段內「隱藏全部」而不是「拒絕登入」：登入、帳號頁、管理功能不受影響，使用者看到空的媒體庫而不是無法解釋的錯誤，且一切仍在同一個內容述詞裡判斷，不需要第二套機制；直投在 `Resolve` 同樣被擋。
- **`allow` 不越過時段**：`allow` 是對「這個條目的內容」的例外（標籤、分級誤判），時段是「這個時間」的限制，兩者語意不同；否則一條 `allow` 就能在宵禁時段看該劇。
- **不用伺服器時區**：容器多半是 UTC、多實例可能不同；「晚上九點」對使用者才有意義。逐時段時區與 G47 客戶端管控時間窗的表示法一致。PostgreSQL 不認得的時區會讓述詞在執行時失敗，所以寫入時就擋（匯入元資料備份時略過，原因 `time_zone_unknown`）。
- **請求時刻而不是語句時刻**：同一請求的多條語句判斷一致，並且可測（注入時鐘、跨日光節約時間的掃描測試 `TestAccessWindowSQLMatchesReference`）。
- **預覽用真實的統一述詞**：重新推導「會多看到什麼」容易與實際過濾不一致；在交易裡實際變更再比較，數字就是套用後的結果，且守門測試仍保證述詞只有一份。代價是成本與「使用者數 × 條目數」成正比（見存取控制文件的效能段），因此一次最多 100 位使用者。
- **模板複製**：連結式模板需要每次過濾都多讀一層並處理「模板與個人設定衝突」，也讓刪除模板變成高風險操作；複製讓每位使用者的有效設定一目了然，稽核也只記實際變更。

## 後果

- 統一述詞多了兩個每列的索引探查（`user_blocked_keywords` 主鍵、`user_access_windows` 主鍵）；只有 `content_filtered` 的使用者才會走到，沒有關鍵字的使用者在第一個探查就停止。
- 已在進行的直投串流不會因進入時段被中斷；下一次 `Resolve` 會依時段拒絕（與其他規則相同）。
- 不同步的時鐘會讓時段提早或延後；以伺服器時鐘為準。
