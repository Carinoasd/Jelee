# ADR 0012：媒體探測採「每檔一個受限子程序＋有界 worker」，不用常駐進程池

- 狀態：已採納（記錄既有決定，G19.5）
- 日期：2026-10-30
- 相關需求：G19.5（並涉及 G09.4、G09.6）
- 相關程式：`internal/platform/process/`（`IsolatedRunner`，`Config.MaxConcurrent`、`Timeout`、`MaxStdoutBytes`）、`internal/platform/proberuntime/`、`internal/adapter/probe/`（`WorkerBridge`）、`internal/platform/sandbox/`
- 相關決定：[ADR 0001](0001-external-process-start.md)、[ADR 0011](0011-windows-media-tool-confinement.md)

## 背景

目錄掃描與重建要對大量檔案取媒體資訊。探測由外部 ffprobe 完成，輸入是不可信的媒體檔。常見的另一種做法是維持一組常駐的 ffprobe／helper 進程池，每個進程反覆處理多個檔案以省下啟動成本。要決定本專案採哪一種。

## 決定

探測採「**每個檔案一個全新的受限子程序**，由**有界的 worker** 驅動」：

1. 每次探測啟動一個新子程序（Linux：本程式的 helper 模式，套用 Landlock、seccomp、rlimit 後 `execveat` 成已驗證的 ffprobe；Windows：受限 token＋Job Object 直接啟動 `ffprobe.exe`），媒體以 `fd:` 從繼承的 stdin 讀入，讀完即結束，程序不重用。
2. 同時存在的子程序數有上限：`IsolatedRunner` 的 `MaxConcurrent`（中繼資料 2；封面與章節圖各 1），超過就在 Runner 內排隊，不會無界產生程序。上層由背景工作（job）驅動探測，同時進行的探測請求與每庫配額另有上限（`probe_cache_quota`、`probe_library_quota`，見[探測驗證](../probe-verification.md)）。
3. 每次執行有固定逾時（中繼資料 30 秒、封面 20 秒、章節圖 30 秒）、輸出上限（stdout 4 MiB，封面與章節圖 16 MiB，stderr 64 KiB）與私有暫存目錄；逾時、取消或超出輸出上限就終止整個程序群組（Windows 為整個 Job）。
4. 探測身分（`ProbeIdentity`）描述的是「這個固定執行方式」；程序模型不屬於身分，但任何放寬隔離的改動都必須改 `MetadataPolicyVersion`／`WindowsMetadataPolicyVersion`。

## 理由

- **隔離。** 輸入是不可信的檔案，解析器漏洞是主要威脅。每檔一個新程序，漏洞即使被觸發，攻擊者拿到的是一個只活一次、沒有前一個檔案內容、讀不到其他檔案（Landlock 只授權該次已開啟的 fd 與固定的程式與函式庫）的程序；常駐程序則會把前一個檔案造成的記憶體狀態帶進下一個檔案，一個惡意檔案就能影響後續所有檔案的結果。
- **失敗半徑。** ffprobe 對損壞檔案可能崩潰、無窮迴圈或吃光記憶體。單檔程序的失敗只影響該檔（記為該檔的探測失敗並快取負結果），不需要偵測「進程池成員已壞」、重啟與重送被中斷的工作，也不會因一個壞檔拖垮同一進程正在處理的其他檔案。
- **每程序限制可在建立時一次到位。** Linux 的 seccomp、Landlock 與 `RLIMIT_AS`／`RLIMIT_CPU`／`RLIMIT_NPROC` 都是對「這個程序」套用且不可放寬、也無法對已在跑的程序按檔案重設；Windows 的受限 token 與 Job（單程序、記憶體 2 GiB、CPU 30 秒、禁止子程序）同理。常駐程序要嘛累計用量（CPU 秒數、位址空間碎片）讓限制失去「每檔」的意義，要嘛得為每個檔案重新建立限制，那就等於重新啟動程序。
- **記憶體回收。** ffprobe 與其解封裝器在處理後不保證釋放全部記憶體；程序結束由作業系統確實回收。長時間掃描數十萬檔時，不需要靠「處理 N 個檔案後重啟」之類的啟發式。
- **簡單可驗證。** 沒有程序間協定、沒有工作重送、沒有健康探測迴圈；失敗模式只剩「啟動失敗」「逾時」「非零結束」「輸出過大」，每一種都有固定錯誤碼，並能以故意無效的健康位元組驗證（`jelee-cli doctor probe`）。

## 代價

- **啟動延遲。** 每檔都要付一次程序建立、（Linux）helper 的驗證與沙箱設定、（Windows）取得受限 token 與建立 Job 的成本，通常是數十毫秒量級（Windows 較高）。對小檔案與大量檔案的庫，這是吞吐量的主要開銷；常駐進程池可以省掉它。
- **無法跨檔案重用解析狀態。** 沒有共用的解析器快取；每檔重新載入函式庫與初始化。
- **吞吐量靠並行度與快取補償。** 並行度受 `MaxConcurrent` 與主機核心數限制；其餘靠探測快取（`probe_cache`，依檔案指紋、工具身分命中）讓第二次起不再啟動程序，掃描只對新增與變動的檔案付成本。

## 何時重新評估

任一情況成立就重新開評估（需新的 ADR 與驗證）：

- 實測（擁有者清單的 Linux 規模量測與 Windows C41）顯示啟動成本在典型庫的首次掃描占總耗時的主要部分（例如超過一半），且提高 `MaxConcurrent` 已因 CPU 或 I/O 飽和無法再改善。
- 出現能在**不跨檔案共用可變狀態**的前提下重用程序的方式（例如每個重用程序在處理前由父程序重新套用相同的限制，且有可驗證的「工作之間狀態清空」證明），並且各平台的限制都能以同等強度維持。
- 上游工具改為提供批次、可在單一受限程序內安全處理多個不可信輸入的模式。
- 部署平台沒有廉價的程序建立（例如某些容器或雲端環境的程序建立成本異常高）。

在此之前，不引入常駐進程池，也不放寬「一檔一程序」的隔離單位。
