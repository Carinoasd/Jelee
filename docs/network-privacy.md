# 網路隱私與公開入口

**客戶端直連公網 IP 時，該 IP 不可能對該客戶端隱藏。** 客戶端必須知道連線目的位址；刪除回應中的 IP、改用 HTTPS 或換成網域名稱，都不能抹除它已使用的網路位址。HTTP／HTTPS 的一般連線流程會解析主機名稱並連至對應位址；這裡的隱私結論是依該流程推得。[RFC 9110 §4.3.2–4.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.3.2)

## 公網位址與來源主機

| 公開方式 | 客戶端可知道的位址 | 能限制的資訊 |
| --- | --- | --- |
| 公網 IP 直連 | 公開服務 IP | 應用可避免額外回顯內網／資料庫位址 |
| 網域直接指向同一主機 | DNS 解析得到的服務 IP | 網域不會隱藏同一台主機的 IP |
| 獨立反向代理 | 代理端點 IP | 限制来源直連及避免回顯來源位址後，可減少來源主機曝光 |

反向代理有自己的連線邊界，不能把「回應沒有位址」當作「來源主機不可被找出」的證據。來源主機的防火牆、DNS 歷史與其他公開服務仍須另外檢查；這份文件不宣稱已完成這些部署驗收。

## 目前 Go 服務的行為

- 直接啟動的預設监听為 `127.0.0.1:8097`，`JELEE_LISTEN` 可明確改寫；要公開到區域網路，需配置明確 IP 與連接埠。
- 容器映像內設定 `0.0.0.0:8097`；Compose 對宿主只發布 `127.0.0.1:8097`。容器內监听與宿主公開範圍必須分開核對。
- `JELEE_ALLOWED_HOSTS` 驗證實際 Host，代理應送出已允許的公開主機名。偽造的 `Forwarded`／`X-Forwarded-Host` 不會覆寫 Host 驗證或提升權限。
- 登入限流與帳號稽核預設使用傳輸對端 `RemoteAddr`；配置可信CIDR後才採嚴格XFF鏈的有效地址。未可信標頭會忽略並記固定告警；未配置可信代理時，使用者仍共用代理IP限流額度。詳見[可信代理](trusted-proxies.md)。
- 請求完成日誌目前只記 requestId、方法與耗時；錯誤回應使用安全固定訊息。這不表示帳號稽核、資料庫或代理日誌從不保存地址。
- HTTPS 在代理終止時，Go 服務收到的請求通常沒有直接 TLS 狀態；目前服務只在直接 TLS 請求加入 HSTS。代理端的 HTTPS、憑證及回應標頭需由部署另外配置。

目前已實作 `JELEE_TRUSTED_PROXIES`／JSON `trustedProxies` 的CIDR與告警，但沒有 `PUBLIC_URL` 設定。完整公開URL重建與公網代理部署驗收仍待G11.1／G11.2後續工作。`Forwarded` 可以由客戶端或中間節點修改；應根據已驗證的代理信任邊界使用，並避免把整條鏈複製到回應。[RFC 7239 §8.1–8.2](https://datatracker.ietf.org/doc/html/rfc7239#section-8.1)

## 部署核對

1. 依[部署文件](deployment.md)保持媒體只讀與資料庫隔離；核對實際 listener、容器 ports 與宿主防火牆。
2. 從外部網路核對只有預期代理入口可連線，並測試來源主機不能被繞過代理直連。
3. 對 Host／轉發標頭、登入限流與公開錯誤執行回歸；檢查重定向、WebSocket、公開 OpenAPI 與代理日誌是否額外暴露地址。
4. 以實際部署的客戶端核對 DNS、TLS、代理與來源連線位址；不要用 localhost 單元測試代替公網驗收。

本階段完成 G11.8 指定文件與隱私聲明，並重新執行現有 Host、傳輸對端與登入限流三項回歸。可信代理已有CIDR／XFF接線；SSRF、WebSocket／完整部署漏洩矩陣尚未實現或驗收，G11整體未完成。[驗證證據](evidence/network-privacy-documentation.json)。
